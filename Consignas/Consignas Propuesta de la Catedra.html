Trabajo Práctico Final 2026 Sistema de Gestión de Coworking y Reservas

Proyecto integrador anual

Objetivo general

Desarrollar una aplicación de escritorio en C# con Windows Forms que permita administrar un espacio de coworking, sus recursos y las reservas realizadas por los clientes.

El trabajo debe integrar contenidos desarrollados durante ambos cuatrimestres, combinando Programación Orientada a Objetos, interfaz gráfica, persistencia en MySQL y organización progresiva del código.

Importante: el proyecto comienza con los contenidos ya trabajados. Algunos requerimientos se incorporarán durante las próximas clases a medida que sean desarrollados en la materia. No se espera que todos estén implementados desde el primer día.
ANÁLISIS ↓ BASE DE DATOS ↓ OBJETOS Y REGLAS ↓ WINDOWS FORMS ↓ INTEGRACIÓN CON MYSQL ↓ MANEJO DE ERRORES ↓ ORGANIZACIÓN DEL ACCESO A DATOS ↓ JSON / CONFIGURACIÓN ↓ PRUEBAS Y PRESENTACIÓN FINAL
Criterio general: priorizar que cada requerimiento tenga una función real dentro del sistema. No agregar clases, interfaces, procedimientos o controles únicamente para “cumplir”.

Escenario del sistema

Un espacio de coworking dispone de distintos recursos que pueden ser utilizados por clientes mediante reservas. El sistema debe permitir registrar los recursos, administrar clientes, generar reservas y consultar su estado.

Recursos posibles

  • salas de reunión;
  • puestos de trabajo;
  • oficinas privadas;
  • otros recursos que el grupo proponga y justifique.

Cada recurso posee características comunes —identificación, nombre, ubicación, estado— y características particulares según el tipo de recurso.

Operación principal

Un cliente debe poder reservar un recurso para una fecha y horario determinados. El sistema debe impedir situaciones inconsistentes, por ejemplo:

  • reservar un recurso inexistente;
  • reservar un recurso que no se encuentra disponible;
  • superponer reservas para el mismo recurso;
  • registrar datos inválidos;
  • eliminar información necesaria para operaciones existentes.
El dominio puede ampliarse con servicios adicionales, estados de reserva, costos, cancelaciones u otros elementos, pero el crecimiento del sistema debe mantenerse controlado.

1. Base de datos MySQL

Esta parte debe resolverse y probarse antes de comenzar la integración con C#.

Modelo mínimo

La base debe incluir como mínimo las siguientes entidades conceptuales:

Clientes

Personas que pueden realizar reservas.

Recursos

Elementos del coworking que pueden ser reservados.

Tipos de recurso

Clasificación de salas, puestos, oficinas u otros.

Reservas

Relación entre un cliente, un recurso y un período de uso.

El grupo puede ampliar el modelo si el diseño lo requiere. Toda tabla adicional debe estar justificada.

Requisitos de implementación

  • Definir claves primarias y claves foráneas.
  • Utilizar tipos de datos adecuados.
  • Incorporar restricciones que ayuden a preservar la integridad.
  • Cargar datos iniciales suficientes para probar el sistema.
  • Evitar información duplicada que corresponda modelar mediante relaciones.

Procedimientos almacenados

Crear procedimientos para las principales operaciones de escritura del sistema. Como mínimo:

  • alta de cliente;
  • alta de recurso;
  • modificación de recurso;
  • alta de reserva;
  • cancelación o modificación de una reserva.
No es obligatorio que cada SELECT se convierta en un procedimiento. Elegir el objeto de base de datos adecuado según la operación.

Vistas

Crear al menos dos vistas útiles para la aplicación. Ejemplos:

  • detalle completo de reservas con datos del cliente y del recurso;
  • resumen de recursos con estado o cantidad de reservas.

Función almacenada

Crear al menos una función definida por el usuario que tenga una utilidad real. Ejemplos posibles:

  • determinar disponibilidad;
  • calcular duración;
  • calcular un importe si el grupo incorpora costos.

Trigger

Incorporar al menos un trigger con una finalidad justificada. Se recomienda utilizarlo para una auditoría pequeña de una operación importante.

Antes de pasar a C#:
probar en Workbench procedimientos, vistas, función, restricciones y trigger. Guardar el script completo de creación de la base.

2. Programación Orientada a Objetos

El proyecto debe recuperar contenidos importantes del primer cuatrimestre y utilizarlos dentro de una aplicación real.

Clase abstracta

Definir una clase abstracta que represente un concepto común del dominio. Una posibilidad es:

Recurso ├── Sala ├── PuestoTrabajo └── OficinaPrivada

La clase abstracta debe aportar atributos, propiedades o comportamiento común. Las clases derivadas deben justificar su existencia mediante características o comportamiento propio.

Herencia y polimorfismo

Utilizar herencia de manera funcional. El proyecto debe contener al menos una situación donde una referencia del tipo base pueda trabajar con diferentes objetos derivados.

Interfaz

Definir al menos una interfaz asociada a una capacidad o comportamiento concreto del sistema. Por ejemplo:

public interface IReservable { bool PuedeReservarse(DateTime fecha); }
El ejemplo es orientativo. La interfaz final debe diseñarse de acuerdo con el modelo elegido y no copiarse automáticamente si no resulta adecuada.

Colecciones

Utilizar colecciones genéricas de .NET cuando sean necesarias para resolver una tarea concreta de la aplicación. No se exige crear estructuras genéricas propias ni utilizar LINQ como requisito del trabajo.

Gestión de responsabilidades

Evitar que todo el comportamiento del sistema quede concentrado dentro de los formularios. Las clases del dominio deben representar información y reglas que les correspondan.

3. Aplicación Windows Forms

Construir una interfaz funcional y clara. El diseño visual será considerado, pero no se evalúa como un concurso de estética.

Módulos mínimos

  • gestión de clientes;
  • gestión de recursos;
  • gestión de reservas;
  • consulta de reservas y disponibilidad.

Controles esperados

Utilizar los controles que correspondan al problema, por ejemplo:

  • DataGridView para listados;
  • ComboBox para seleccionar datos relacionados;
  • DateTimePicker para fechas;
  • NumericUpDown cuando resulte adecuado;
  • TabControl, menús o formularios modales cuando mejoren la organización.
Los ComboBox deben mostrar descripciones comprensibles para el usuario y conservar internamente el identificador necesario para operar con la base.

Conexión

Utilizar una clase centralizada ConexionBD. No repetir la cadena de conexión en los formularios.

Windows Forms ↓ clases / lógica ↓ acceso a datos ↓ ConexionBD ↓ MySQL

La separación definitiva del acceso a datos será incorporada posteriormente durante la cursada.

4. Manejo de errores

Las operaciones críticas deben contemplar errores provenientes de MySQL.

Error genérico

Capturar errores del proveedor mediante:

catch (MySqlException ex) { // tratamiento del error proveniente de MySQL }

Error personalizado

Al menos una regla de negocio debe ser validada desde la base mediante:

SIGNAL SQLSTATE '45000' SET MESSAGE_TEXT = 'Mensaje de negocio';

La aplicación deberá reconocer ese SQLSTATE y mostrar al usuario el mensaje correspondiente.

SP detecta condición inválida ↓ SIGNAL 45000 ↓ MySQL propaga excepción ↓ MySqlException en C# ↓ ex.SqlState == "45000" ↓ mensaje específico

Errores no específicos de MySQL

Puede utilizarse un segundo catch (Exception ex) para situaciones generales de la aplicación.

No utilizar bloques catch vacíos. Los errores no deben ocultarse.

5. Requerimientos evolutivos

Los siguientes elementos forman parte del objetivo final, pero serán incorporados cuando sean desarrollados en clase.

Acceso a datos / DAO Próximamente

Retirar progresivamente del formulario el código específico de acceso a MySQL y ubicarlo en clases responsables de esas operaciones.

Form ↓ lógica / dominio ↓ RecursoDAO / ReservaDAO / ClienteDAO ↓ ConexionBD ↓ MySQL
No se exige una arquitectura empresarial completa. El objetivo es comprender separación de responsabilidades y evitar que el formulario concentre interfaz, reglas y acceso a datos.

JSON Próximamente

Incorporar una operación de importación o exportación mediante JSON. Debe utilizar objetos reales del sistema y tener una finalidad concreta.

Ejemplos:

  • exportar catálogo de recursos;
  • exportar reservas;
  • importar recursos desde un archivo preparado para ese fin.

Configuración externa Próximamente

Retirar del código fuente los datos de conexión que no deberían quedar escritos directamente dentro de ConexionBD y leerlos desde la configuración de la aplicación.

Estos requisitos serán explicados antes de ser exigidos. No deben implementarse anticipadamente utilizando soluciones que el grupo no pueda justificar.

Entregables

La entrega final deberá incluir:

  • solución completa de Visual Studio;
  • script SQL capaz de crear la base desde cero;
  • datos mínimos de prueba;
  • todos los procedimientos, vistas, funciones y triggers utilizados;
  • archivo JSON de ejemplo cuando se incorpore ese contenido;
  • breve documentación técnica del sistema;
  • diagrama del modelo de datos;
  • diagrama de clases simplificado;
  • instrucciones necesarias para ejecutar el proyecto.

Documentación mínima

Explicar brevemente:

  • objetivo del sistema;
  • modelo de datos;
  • clases principales;
  • uso de herencia, abstractas e interfaces;
  • objetos de MySQL utilizados y por qué;
  • manejo de errores;
  • decisiones importantes tomadas por el grupo.
Presentación: todos los integrantes deberán poder explicar las partes principales del proyecto y justificar las decisiones adoptadas.
